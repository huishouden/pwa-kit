# Languages

Every Huishouden app is fully translated: English (`en`), Spanish (`es`) and Dutch (`nl`). This is
the reference for the kit's `./i18n` and `./react/i18n` and the step-by-step for translating an app.

> **Native review wanted.** The Spanish and Dutch were written carefully but not by native
> speakers. A native speaker should review both catalogues (the kit's `src/locales/{es,nl}/` and
> each app's `src/locales/{es,nl}.json`) before we call them final; open an issue with corrections
> rather than editing one app alone, so the glossary below stays the single source.

## How it works

- **One language per member, for the whole suite on every device.** It is stored on the household,
  `households/{id}.langs[email]`, which every member's device reads with the household and only
  that member writes (the rules). `watchHousehold` follows it (`./member-lang`): the first time a
  member opens an app with none stored, the language that device shows is stored (the device's
  languages, `navigator.languages`, matched to the first one we speak, else English, or a language
  chosen there); afterwards a change on any device is stored and every other device follows. A
  member of several households keeps the same language in each (the one the apps use leads; with
  none stored there, the language stored in another joined household is taken before the
  device's). Only households the member has joined are written: an invitation never acted on gets
  nothing. The
  app bar's menu offers it under "Language": English / Español / Nederlands, each named in
  itself; signed out, the device's own Automatic is offered too.
- **localStorage is the boot cache.** The choice is also kept in `localStorage` under `hh-lang`,
  so a page paints in it before the household arrives. All apps share one origin
  (docs/one-site.md), so open tabs follow at once (the `storage` event).
- **Before the first paint.** `pwaApp` inlines `LANG_BOOT_SCRIPT` in `<head>` (like the theme), so
  `<html lang>` is right before the bundle loads. The app awaits `startI18n()` before its first
  render, which loads the language's catalogues, so no English flashes.
- **Catalogues.** Flat JSON objects of ICU-style messages. The kit's own (`src/locales/<lang>/<area>.ts`,
  merged into `src/locales/<lang>.ts` by `scripts/locales-index.ts`) and the app's
  (`src/locales/{en,es,nl}.json`). English is bundled; Spanish and Dutch are separate chunks
  loaded when chosen (the service worker precaches them, so they work offline). A key missing
  from a translation falls back to English for that key only.
- **Typed keys.** The app merges its English catalogue's type into `AppMessages`, so `t('typo')`
  fails `tsc`. The kit's keys are typed the same way (`KitKey`), and its Spanish and Dutch must have
  exactly the English keys (`satisfies CatalogueOf<typeof en>`).
- **One locale formats everything**: `getLocale()` / `useLocale()`. It is the chosen language
  with the device's region where it has one: the device's own tag for that language (en-GB, es-MX,
  nl-BE), else the language plus the device's region (Spanish on an en-US phone is `es-US`: dollars,
  miles, 12-hour clock), else `en-US`, `es-419`, `nl-NL`. Every kit date, time, number, money,
  distance, relative-time and list formatter defaults to it. 12 or 24 hours follows the locale.
- **Money** is shown in the household's currency (`households/{id}.currency`, ISO 4217, US dollars
  when unset; `watchHousehold` applies it with `setCurrency`), formatted in the active locale with
  the narrow symbol: `$1,234.50` (en-US, es-US, es-MX), `1234,50 $` (es-ES), `$ 1.234,50` (nl). `parseCents` accepts either
  decimal mark ("12,50" and "12.50" are both 12.50).
- **Data stays as entered.** Item names, notes, payees, people's names: never translated. Sample
  data in the signed-out demo may stay English. Parsing of outside text (emails, statements,
  labels, pasted listings) keeps matching the languages those texts come in.

## Messages

```json
{
  "upcoming.title": "Upcoming",
  "upcoming.dueCount": "{count, plural, =0 {Nothing due} one {# bill due} other {# bills due}}",
  "upcoming.paidBy": "{name} paid {bill}",
  "upcoming.who": "{role, select, admin {An admin} other {Someone}} changed it",
  "settings.dayOfMonth": "On the {day, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}"
}
```

- `{name}` inserts a variable (numbers are formatted in the locale). `{n, number}` likewise.
- `{n, plural, =0 {…} one {…} other {…}}`: `#` is the number. Spanish also has `many` (a million);
  a missing form falls back to `other`, which is what we want. Dutch and Spanish need only
  `one`/`other` (plus `=0` when the sentence changes).
- `{x, select, a {…} b {…} other {…}}`: a word chosen by a value (a role, a kind). Every
  `plural`/`select` needs `other`.
- `{n, selectordinal, …}`: English ordinals. Spanish and Dutch rarely need it (`el día {n}`, `de {n}e`).
- No quoting: an apostrophe is just an apostrophe; a message never contains a literal `{` or `}`.
- **Whole sentences, never concatenation.** Word order differs: "Every 2 weeks on Friday" is
  "Cada 2 semanas, los viernes" and "Elke 2 weken op vrijdag". Build one message per sentence
  shape with variables, not `t('every') + n + t('weeks')`. Lists go through `formatList(items)`
  ("a, b, and c" / "a, b y c" / "a, b en c").
- **Keys** are `area.thing` in lower camel case: the screen or component, then what it is
  (`billDialog.title`, `upcoming.empty`, `toast.saved`). Reuse a key only where the meaning is the
  same, not just the English: "Clear" a filter and "Clear" weather are two keys.
- The kit's `common.*` keys (Save, Cancel, Delete, Undo, Try again, ...) work in any app's `t()`.

## API

`@huishouden/pwa-kit/i18n` (no React):

| | |
|---|---|
| `registerMessages(en, { es: () => import('./locales/es.json'), nl: () => import('./locales/nl.json') })` | Adds the app's catalogue. Once, at start-up, in `src/i18n.ts`. |
| `startI18n(): Promise<void>` | Reads the choice, loads its catalogues, follows other tabs. Await before the first render. |
| `t(key, vars?)` | The app's message, else the kit's, in the active language. |
| `getLang()`, `getLangChoice()`, `setLangChoice(choice)`, `onLangChange(fn)` | The language, the stored choice, changing it (every app), listening. |
| `getLocale()` | The formatting locale. |
| `formatNumber(n)`, `formatList(items, { type })`, `capitalize(s)`, `compareText(a, b)` | Locale-aware helpers. |
| `inLangs(langs, fn)`, `inEveryLang(fn)`, `withLang(lang, fn)`, `loadLang(lang)` | Text built for other members (notifications, to-dos, agenda items). |
| `setLangForTests(lang, deviceLanguages?)`, `resetI18nForTests()` | Unit tests and screenshots. |
| `LANGS`, `LANG_NAMES`, `LANG_KEY`, `LANG_BOOT_SCRIPT` | Constants. |

`@huishouden/pwa-kit/react/i18n`: `useT()` (re-renders on a change; a new function each time, so
memo dependencies work), `useLocale()`, `useLang()` (`{ lang, choice, locale, setChoice }`).

Formatters that follow the locale: `./time` (`shortDate`, `longDate`, `monthYear`, `dueWords`,
`dueText`, `dueHeadline`, `inDays`, `daysAgo`, `relativeDay`, `formatSpan`, `formatDuration`,
`formatAgo`, `agoWords`, `formatTime`, `formatDayLong`, `formatDateLong`, `formatDayShort`,
`weekdayShort`, `monthShort`, `formatYmd`, `clockWords`, `monthName`, `weekdayName`, `ordinal`),
`./money` (`formatCents`, `formatMoney`, `centsToInput`, `parseCents`), `./places`
(`formatDistance`), `./hours` (`describeDay`), and every kit component. Never call
`toLocaleDateString(undefined, …)`, `Intl.*('en-US', …)` or `navigator.language` in app code:
use these, or `getLocale()`.

## Translating an app, step by step

This is mechanical; an agent can do it from this list. The Bills repo is the worked example.

1. **Kit**: depend on the kit release with `./i18n` (v0.60.0 or later).
2. **Catalogues**: create `src/locales/en.json` with every visible English string of the app,
   keyed `area.thing`. Then `es.json` and `nl.json` with the same keys, translated with the glossary
   below. Apostrophes are fine; braces only for variables.
3. **`src/i18n.ts`**, exactly:

   ```ts
   import en from './locales/en.json';
   import { registerMessages } from '@huishouden/pwa-kit/i18n';
   type AppEn = typeof en;
   declare module '@huishouden/pwa-kit/i18n' { interface AppMessages extends AppEn {} }
   registerMessages(en, { es: () => import('./locales/es.json'), nl: () => import('./locales/nl.json') });
   export { t, startI18n } from '@huishouden/pwa-kit/i18n';
   export { useT, useLocale, useLang } from '@huishouden/pwa-kit/react/i18n';
   ```

   Every module that shows text imports `t`/`useT` from this file (not from the kit directly), so the
   catalogue is registered first, in unit tests too. `tsconfig.json` needs `"resolveJsonModule": true`.
4. **`main.tsx`**: `startI18n().finally(() => createRoot(root).render(<App />))`, with
   `import { startI18n } from './i18n'`.
5. **Replace every literal**: JSX text; `aria-label`, `title`, `placeholder`, `alt`, `label`,
   `hint` and other text props; toasts (`notify`, `fail`); error and empty-state sentences; dialog
   titles and buttons; status words; the app bar's `app` name (`t('app.name')`). Components call
   `const t = useT()`; plain modules call `t` and are re-run by the components that render them.
   Text computed at module load (a `const LABELS = { … }` with English) becomes a function or a map
   of keys: `const LABEL_KEYS = { paid: 'status.paid' } as const` and `t(LABEL_KEYS[s])`.
6. **Formatting**: dates, times, numbers and money only through the kit formatters above (or
   `Intl.*(getLocale(), …)` / `useLocale()`); no English month or weekday arrays, no `'en-US'`.
   Amount inputs: `type="text" inputMode="decimal"` with `parseCents`/`centsToInput`, which read and
   write the locale's decimal mark.
7. **Data stays as entered**: don't translate stored values. A value stored as an id (`'paid'`) is
   translated where shown; a value stored as English text (an old category) stays stored as is and
   is shown as stored unless it is one of the app's own fixed choices, which map to keys for display.
   Wrap household data in `translate="no"` where browser translation would mangle it (names).
   Contact roles an app offers (`ContactDialog`'s `roles`) are such fixed choices: keep them in
   English and pass `roleLabel={(r) => (ROLE_KEYS[r] ? t(ROLE_KEYS[r]) : r)}` (chips and field show the label, the
   English role is saved; typing a label saves its role), and show `ContactCard`'s `role` the same way.
   Pass the same function to `groupContacts(contacts, ROLES, roleLabel)`, so a role someone typed as
   its shown name ("Plomero") joins that role's group.
8. **Text other members read**: reminders, to-dos and agenda items are written once and read on
   every reader's device, each in the reader's language. Wrap the builder that makes them, which
   must be synchronous and give the same records in the same order each time:

   ```ts
   syncReminders(db, id, 'bills', await localizeReminders(() => billReminders(bills, now)), me);
   syncTodos(db, id, 'bills', await localizeTodos(() => billTodos(bills, now)), { by: me });
   syncAgenda(db, id, 'bills', await localizeAgenda(() => billAgenda(bills)), { by: me });
   ```

   Its own `title`/`body`/`detail` are in the writer's language, and `texts` (title, body or
   detail, and a to-do's button words) only in the other languages its readers use
   (`./reader-langs`): a reminder's named recipients, else a personal item's `audience`, else every
   member who may see it (admins and members only when private or from Spending or Bills), each
   by their stored language, the writer's for a member with none stored. A household that reads one
   language stores no `texts`; the builder runs once per language needed. The languages come from
   the household `watchHousehold` last saw (`setReaderHousehold`); a server passes
   `{ household, writer }` (the household tools do). With no household known every language is
   stored. Readers take theirs, else the record's own words: the notify Worker the recipient's
   stored language (else their subscription's `lang`), the portal `todoWords(item)` and
   `agendaWords(item)`, calendars and the assistant the member's language. Records written before
   are rewritten with fewer languages by the app's next sync. Kit builders already do it
   (`remindersForCourseInEveryLang`).
9. **Run the check**: `bunx pwa-i18n-check --strict` (CI runs it without `--strict`: catalogue
   errors fail, literals warn). Keys built at run time (`t(\`status.${s}\`)`) need a comment
   `// i18n-dynamic: status.` so they don't count as unused. A line that is genuinely not text (a
   brand, code, a unit symbol) takes `// i18n-ignore` (or `{/* i18n-ignore */}` in JSX) on it or
   the line above; use it sparingly.
10. **Tests**: unit tests stay in English (the default). Add `e2e/i18n.spec.ts` with
    `expectLocalized(page, 'es', { words: [...] })` and `'nl'` on the signed-out sample, plus one
    interaction (open a dialog) checked in that language. List the app's own distinctive English
    chrome words in `words` (its tab names, its main buttons). Assert buttons by their exact role
    name (`getByRole('button', { name: 'Cancelar', exact: true })`): `toContainText('Cancel')`
    also matches inside "Cancelar".
11. **Screenshots**: add Spanish and Dutch phone screenshots to the PR (`useLanguage(page, 'es')`
    before `goto`).
12. **Review**: the PR description lists anything left in English and why.

## Pitfalls

- **Capitalized words mid-sentence.** `dueWords` capitalizes for a label ("Today", "Hoy"); in a
  sentence use `dueWords(due, today, { inline: true })` ("vence hoy", not "vence Hoy").
- **Longer labels.** Spanish and Dutch buttons are longer: give a headline beside buttons a
  `basis-*` so it can't be squeezed to a few characters on a phone, and check 360 px.
- **Text computed once.** A module-level constant with English (`const LABELS = {…}`) never
  changes language: make it a function, or getters (`get label() { return t('…') }`) on objects
  read at render.
- **Stored English.** Words written into Firestore by one device (a to-do's button, an agenda
  detail) are read by others: use `localizeTodos`/`localizeAgenda`/`localizeReminders`, never the
  writer's `t()` alone.
- **Amounts typed with a comma.** `parseCents` reads "12,50"; older code using `toDecimal` on a
  typed amount read it as 1250. Use `parseCents` for input, `toDecimal` only for imported statements.
- **Local e2e against a linked kit.** With the kit symlinked into `node_modules`, Playwright loads
  `@playwright/test` twice ("Requiring @playwright/test second time"); copy the kit in (without its
  `node_modules`) instead of linking. Installs from git are unaffected.

## Testing

- **Unit**: `setLangForTests('es', ['es-MX'])` switches the page's language and locale without
  storage (await it: it loads the catalogues). In the kit, `resetI18nForTests()` after; in an app,
  `setLangForTests('en')` after, since `resetI18nForTests()` also forgets the app's catalogue
  (registered once, when `src/i18n.ts` is first imported) for every later test in the run. Kit tests check that
  every kit message parses, that Spanish and Dutch have every key with the same variables, and that
  no kit file formats with `undefined`, `'en-US'` or `navigator.language`.
- **E2E** (`@huishouden/pwa-kit/e2e`): `useLanguage(page, lang)` stores the choice before the next
  load; `expectLocalized(page, lang, { path, words, allow })` opens the page in that language,
  checks `<html lang>`, and fails when any of the kit's English chrome words (`ENGLISH_CHROME`:
  Sign in, Sample data, Overdue, Due in, Today, Undo, Cancel, Save, Delete, More, ...) or the app's
  own `words` show in the visible page, app bar included. Text inside `translate="no"`,
  `[data-hh-data]` or `[data-sample-data]` is skipped (household data).
- **CI**: `pwa-i18n-check` in the reusable workflow; the cr reviewer checks that new UI text ships
  in every language (STANDARD.md "Languages").

## Formatting rules

| | English | Spanish | Dutch |
|---|---|---|---|
| Short date | Nov 4 | 4 nov (es-US: nov 4) | 4 nov |
| Long date | Tuesday, November 4 | martes, 4 de noviembre | dinsdag 4 november |
| Time | 7:30 PM (en-US) | 7:30 p.m. (es-US/MX), 19:30 (es-ES) | 19:30 |
| Money (USD) | $1,234.50 | $1,234.50 (es-US, es-MX), 1234,50 $ (es-ES) | $ 1.234,50 |
| Relative | in 3 weeks, 2 days ago | en 3 semanas, hace 2 días | over 3 weken, 2 dagen geleden |
| List | a, b, and c | a, b y c | a, b en c |

- Weekday and month names are lowercase mid-sentence in Spanish and Dutch (Intl gives them so);
  capitalize at the start of a label with `capitalize()`.
- Sentence case for labels in all three languages, as DESIGN.md says for English.
- Keep it short: Spanish runs about 20% longer than English, Dutch about 10%. Buttons and tabs must
  still fit at 360 px; prefer the shorter natural word ("Agregar" over "Añadir un nuevo").
