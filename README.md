# pwa-kit

Building blocks for small installable web apps (PWAs) on Firebase Hosting, shared by a family of
apps that each live in their own repo. Every piece exists because an app hit the problem it solves.

| Piece | Path | What it does |
|---|---|---|

| Firestore | `@huishouden/pwa-kit/firestore` | `initFirestore(app, { auth })`: the persistent multi-tab cache every app uses. `setDoc`, `updateDoc`, `deleteDoc`, `addDoc`, `writeBatch`, `deleteField`, `serverTimestamp`, `arrayUnion`, `arrayRemove`, `increment` with Firestore's arguments (`updateDoc` and `batch.update` take an object, not field-path/value pairs): each write is also noted in localStorage before the call returns and forgotten once the server has taken or refused it (Firestore's local cache may be memory only, when IndexedDB can't be opened), so a write made just before the app closes or reloads, online or offline, is written again when the same person next opens it, unless the server's copy of the document (offline, or with a write to it still in Firestore's own queue, the local cache's) shows it landed (every field as the note sets it), a newer edit (`updatedAt`, also another member's) overtook it, or, for an `increment`, Firestore's own queue still holds a write to the document (so it counts once); several writes to one document in a note are repeated together, in order, from the first one not yet there, so a replay never leaves the document at an earlier write's value (a document without `updatedAt` can't tell another member's newer write from its own lost one, so it is repeated only when the server doesn't show it; offline with no copy of the document, a set or delete is repeated unchecked, as Firestore's own queue would; `updatedAt` and the note's time come from device clocks); an update to a document the device has never read waits while the server can't be reached, is left out when the rules refuse the read, and otherwise is written once the server shows the document exists; notes older than a week are dropped. `forgetOutbox(db, { signOut })` gives the person's unsent writes 3 s, removes their notes, then runs `signOut` (no new notes for them in between; noting resumes if they are still signed in); Firestore's own cache stays. `signOutEverywhere` calls it. Without `initFirestore` they are Firestore's own. CI's `pwa-write-check` fails an app that imports a write function from `firebase/firestore`. |

## Install

```sh
bun add -d https://github.com/huishouden/pwa-kit/releases/download/vX.Y.Z/pwa-kit-X.Y.Z.tgz
```

Each release carries the package as a tarball (public, no token), built in CI; `dist/` is not in git.
Releases before the first tarball (v0.105.0 and earlier) install as
`@huishouden/pwa-kit@github:huishouden/pwa-kit#vX.Y.Z` (spell out the package name).

## Versioning

Tags `v0.x.y` are immutable; `v0` moves to the latest `v0.x.y`. Workflows reference an exact tag
(`@vX.Y.Z`, as `hh dev bump-kit` sets them) and packages install from the release tarball
(`pwa-kit-X.Y.Z.tgz`) of the same tag. Releases through v0.105.0 have no tarball and install from the
git tag.

## Household rules

Apps put their data under `households/{householdId}/<collection>`. The project's single rules file
needs the household document rules (members read; admins edit `members` and `roles`, members
`name`; each member appends only their own email to `joined`; creating starts with only the
creator) plus, per app, read and write rules by role (`huishouden/rules` README "Roles"):

```
match /households/{householdId}/<collection>/{doc} {
  allow read: if isMember();
  allow delete: if canRemove();                 // admins and members, or the helper who added it
  allow create, update: if writer(['done']);    // and the field checks
}
```

### Filling a contact when OpenStreetMap doesn't know the business

OpenStreetMap often lacks local businesses (a vet hospital, a groomer). Three free ways in, all
landing in `ContactDialog` for the person to check, with anything not understood listed under it:

1. **Screenshot.** In Google Maps, open the business and take a screenshot; in the dialog, "Fill
   from a screenshot". Read on the device (the OCR engine, a few megabytes, downloads on first use).
2. **Paste.** Copy the listing's text (Google Maps on a computer, Apple Maps, Yelp, or Google
   Maps' Share text) and use "Paste listing text".
3. **Share** (Android and desktop Chrome, installed app): Google Maps → Share → the app. iOS
   doesn't support web share targets, so on iPhone use a screenshot or paste.

```tsx
// vite.config.ts: pwaApp({ ..., shareTarget: true })
import { clearSharedPlace, readSharedPlace } from '@huishouden/pwa-kit/places';
const shared = readSharedPlace(window.location); // null on an ordinary launch
if (shared) clearSharedPlace();
<ContactDialog contact={null} app="pet" roles={ROLES} prefill={shared?.place} onSave={save} onClose={close} />
```

The share target launches `/?share_title=…&share_text=…&share_url=…`: browsers replace the query
of a GET share target's action, so the marker is in the parameter names rather than `?share=1`
(hand-made `?share=1&title=…&text=…&url=…` links are read too).

### Filling a contact from the person's own contacts

The landlord, the babysitter, the plumber are usually in the phone already. `ContactDialog` offers
three ways in, each filling the fields for the person to check (first phone and email in their
fields, other numbers and emails with their labels in the notes):

| | iPhone | Android |
|---|---|---|
| **Pick from my contacts** (Contact Picker API) | Not offered: Safari has no contact picker | Chrome: opens the phone's contact list |
| **Import a contact card** (.vcf) | Contacts → the contact → Share Contact → Save to Files, then choose the file | Contacts → the contact → Share → save the .vcf, or choose it straight from Files |
| **Find in my Google Contacts** (signed in) | Yes | Yes |
| **Share a contact to the app** (`shareTarget: { contacts: true }`) | Not available: iOS has no web share targets | Installed app: Contacts → Share → the app |

Google Contacts is read with the People API (`people:searchContacts` and `otherContacts:search`,
scopes `contacts.readonly` and `contacts.other.readonly`; enable `people.googleapis.com` in the
Firebase project). Until Google verifies the app, its consent screen says so; the dialog says to
choose Advanced and continue.

```tsx
// vite.config.ts: pwaApp({ ..., shareTarget: { contacts: true } })
import { clearSharedContact, readSharedContact, type ParsedContact } from '@huishouden/pwa-kit/contacts';
const [shared, setShared] = useState<ParsedContact[] | null>(null);
useEffect(() => void readSharedContact().then((cards) => cards && (setShared(cards), clearSharedContact())), []);
{shared && <ContactDialog contact={null} app="home" roles={ROLES} auth={auth} sharedContacts={shared} onSave={save} onClose={() => setShared(null)} />}
```

A file can only be shared with a POST, which the service worker receives (`hh-share-sw.js`): it
keeps the card in Cache Storage and opens the app at `?share=contact`; `readSharedContact()` reads
it once. A shared place (no card) is sent on as `?share_title=…&share_text=…&share_url=…`, so
`readSharedPlace` works the same with either share target. Browser tests stand in for Google with
`window.__mockGoogleContactsToken` and answer `people.googleapis.com` with `page.route`; `shareContactCard(page, vcf)` in `/e2e` shares a card the way Android does.
